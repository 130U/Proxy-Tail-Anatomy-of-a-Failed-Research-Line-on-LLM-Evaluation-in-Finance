## 2. How continuous scores are obtained, and when they cannot be

First define the tail event in words, then fix binary labels, for example `A=target event`, `B=non-target event`. Each label must be a single token for that model, and leading-space variants must be checked; there are currently no measured token IDs, and the IDs of other models cannot be copied. The prompt should ask only for the label, so that the opening curly brace of JSON does not become the first scored token. There is an official example of using logprobs for classification, but the example does not prove calibration or ranking quality on a financial task. [Official example](https://developers.openai.com/cookbook/examples/using_logprobs).

Chat Completions can use `reasoning_effort="none"`, `logprobs=true`, `top_logprobs=20` and `max_completion_tokens=1`, with the prompt, temperature and other sampling settings fixed. The Responses equivalents are `reasoning={"effort":"none"}`, `include=["message.output_text.logprobs"]`, `top_logprobs=20`; that API's output limit parameter is `max_output_tokens`. Both APIs cap the number of candidates at 20, and the actual return may contain fewer than requested. Short headlines should not rely on automatic context truncation. [Chat parameters](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create), [Responses parameters](https://developers.openai.com/api/reference/resources/responses/methods/create).

If **the same request and the same output position** return valid candidate logprobs for both labels, define

\[
D(x)=\log P(A\mid x)-\log P(B\mid x),\qquad
p_{AB}(x)=\frac{1}{1+\exp[-D(x)]}.
\]

We suggest ranking directly by `D`, to avoid extra floating-point saturation when the sigmoid is close to 1. `p_AB` is only the normalized share of the model output between these two labels, not a calibrated true event probability; non-label outputs must also be watched. If the application needs several tokens to represent the same label, sum over the known candidate set and restate the truncation issue; one cannot take only the most favorable spelling.

The main obstacle is that **top-20 does not guarantee that A and B are included**. A missing candidate cannot be filled in as zero probability; the `-9999` in the documentation is a sentinel for very low probability and also cannot be used as an exact logprob to form a spurious extreme continuous score. Such items should be marked unscorable or as carrying only bounded information. Two separate requests that force outputs A and B respectively and are then subtracted usually do not share the same normalized distribution and cannot be treated as the `D` above. [Definition of return values](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).

Chat's `logit_bias` can add the same positive bias to the verified A/B token IDs, for example `+20` each, to raise the chance that both enter the top-20; in a mathematical model where the same constant is truly added to the same logits distribution, the common bias and the normalizing constant cancel in the log-odds of the two. The official Chat endpoint explicitly lists this parameter, but this check did not find item-by-item `logit_bias` support tables for Luna/Sol, and no live account call was made; the 100-item pilot should test whether the parameter is accepted, the A/B coverage rate, and the score difference on samples where both are visible without bias. This is an executable candidate plan for continuous scoring; it cannot be judged infeasible just because of the top-20 limit, nor can 100% coverage be promised. [logit_bias definition](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).

First run a small trial of about 100 items, 3 runs each, and report the rate at which A/B are both available, the non-label/refusal rate, the variation of repeated scores, and rank changes near the screening boundary. Neither zero temperature nor a fixed seed constitutes proof of determinism; officially, seed is only promised to give best-effort reproducibility. **The main statistics keep all ties at the boundary and report the actual pass-through rate; a deterministic ordering is used only for display, does not fake continuity, and adds no hidden perturbation.** When only one valid label is generated, `finish_reason=length` can be the expected single-token truncation and cannot be judged invalid across the board; empty output, whitespace only, refusal or missing valid candidates cannot be scored. The main comparison should fix one scoring result, and repeat trials test stability separately. [seed and finish reason](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).

| Candidate | Scale reported by the original authors and currently visible content | Usage judgment |

| Bloomberg / Reuters Financial News Dataset | The original repository reports 450,341 Bloomberg and 109,110 Reuters items | **Not chosen.** The original author states explicitly that it is no longer provided online for copyright reasons; we did not look for mirrors that bypass the takedown, nor contact the author. |
| NIFTY | The authors' data card provides 2,111 daily-aggregated samples; each row can contain several headlines, and the card is labeled MIT | **This cannot establish 100,000 independent headlines.** The independent headlines after expansion were not counted; the paper says the sources include WSJ, Reuters and others, and the card label is not enough to prove a license for third-party headline text. |

The sources for FNSPID are the [original authors' repository](https://github.com/Zdong104/FNSPID_Financial_News_Dataset) and the [original authors' data card](https://huggingface.co/datasets/Zihan1004/FNSPID). A 2025-07-24 announcement at the top of the repository README says it is open for commercial and research use; but an older paragraph still restricts commercial use of the code, and the [LICENSE](https://github.com/Zdong104/FNSPID_Financial_News_Dataset/blob/main/LICENSE) is still CC BY-NC 4.0. The broader new announcement and the narrower old license are inconsistent, **which does not amount to a ban on non-commercial research**; it can be kept as the preferred technical candidate for use within the CC BY-NC non-commercial scope with attribution. However, the old restriction refers explicitly to the code, the specific scope of the repository LICENSE with respect to the news text is not stated separately, and an aggregator cannot automatically prove that each news source granted it full text rights. The current HF viewer also shows a data generation error, so the default `load_dataset` path cannot be guaranteed to work without a trial read. All of the above are observations of the release pages, not legal license conclusions.

The basis for the second item is the [original author's repository README](https://github.com/philipperemy/financial-news-dataset). The basis for the third item is the [NIFTY authors' data card](https://huggingface.co/datasets/raeidsaqur/NIFTY) and the [data source section of the authors' paper](https://arxiv.org/html/2405.09747v1). This check read the original repositories through the GitHub connector; license labels on Kaggle or from re-uploaders are not taken as a guarantee of ownership, and the paper's license is not taken as a license for the news text.

What can be advanced now: specify the tail event and the scoring prompt, and after configuring the API complete a very small API trial scoring; for the formal large sample, FNSPID is the preferred candidate, with the non-commercial research scope and the unconfirmed ownership of third-party news text kept in the report. Research use, submitting headlines to an external API and publicly redistributing text are different questions; publishing only IDs, scores and summaries reduces text redistribution but cannot prove the rights of all source parties. This is an evidence limit; no extra generalized license approval is set up, and "downloadable" is not written as "text ownership fully confirmed".

## 4. Small-scale access test of FNSPID: a trial read is possible, and the file head is not a random sample

On 2026-11-16 a read-only check was made of the [original authors' Stock_news directory](https://huggingface.co/datasets/Zihan1004/FNSPID/tree/main/Stock_news) and its [file metadata API](https://huggingface.co/api/datasets/Zihan1004/FNSPID/tree/main/Stock_news?recursive=false&expand=false). The directory contains only the two CSVs below, with no separate headline projection file. `Range: bytes=0-1048575` was sent for both files, and both actual responses were **HTTP 206**, with `Content-Range` matching the requested range.

| File | Exact size from metadata | Complete rows conservatively counted in the first 1 MiB | Exact unique headlines | Number of stock symbols |
| --- | ---: | ---: | ---: | ---: |
| `All_external.csv` | 5,731,397,037 bytes | 4,605 | 4,356 | 5 |
| `nasdaq_exteral_data.csv` | 23,232,979,597 bytes | 152 | 139 | 1 |

The measured CSV header is `Date, Article_title, Stock_symbol, Url, Publisher, Author, Article, Lsa_summary, Luhn_summary, Textrank_summary, Lexrank_summary`; the second file also has a leading `Unnamed: 0` column. The data were decoded strictly as UTF-8 and parsed as CSV, and the last parsed record at the end of the range was conservatively discarded to avoid counting a truncated row as a complete record; the tail of the second file was indeed cut inside an unfinished quoted field. Every counted row in the table has a non-empty headline. Only fields, dates and counts were output; **no headlines were output and no article text was saved**.

The prefix of `All_external.csv` is not globally monotone in date, and a single stock accounts for 2,739 of its rows; this number is a total occurrence count, not a verified length of a contiguous block. The prefix of `nasdaq_exteral_data.csv` belongs entirely to one stock, with dates decreasing from 2023-12-16 to 2023-05-09. This describes only this prefix and cannot be extrapolated to the ordering of the whole file; but it is already enough to reject the practice of "reading the first 20,000 rows as a random sample of financial headlines". After exact deduplication there may still be case/format variants, and different headlines also cannot be treated directly as independent news events.

This Python access read a total of **2,097,790 bytes** of response body: 638 bytes of directory metadata plus two ranges of 1,048,576 bytes each; below the 10 MB cap. The directory web page was also viewed; no whole dataset was downloaded, no paid API was called, and no news was submitted to a model.

**Conclusion on the 100,000-headline pool:** the scale reported by the original authors is sufficient, and low-cost access through HTTP Range has been verified; but this time only the few thousand unique headlines above were actually measured, so it has not been shown that 100,000 deduplicated headlines can be obtained within 10 MB, let alone that events are independent. File byte size or prefix density alone cannot guarantee the number of unique items in the whole dataset.

If `All_external.csv` is adopted as an explicitly bounded candidate population, a simpler next step is a sequential streaming scan: deduplicate with a fixed headline normalization rule, do uniform reservoir sampling over first occurrences of new headlines, and then draw the scoring sample at random from this deduplicated pool. This avoids saving article text and does not pass off the file head as a random sample; but it still requires transferring about **5.73 GB** for that file, and reading only some columns does not automatically reduce the CSV network transfer. If the population is defined as the two files combined, about **28.96 GB** and cross-file duplicates have to be handled. Randomly sampling byte windows can serve only as an access diagnostic or an explicitly labeled block sample; window boundaries, record lengths and stock clustering make it different from uniform headline sampling. None of these scans or samplings was performed this time.
